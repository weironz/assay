# 两步验证（验证器应用）

本系统使用 Better Auth 1.6.23 的 two-factor 插件实现基于时间的一次性密码（TOTP）。用户可在「设置 → 安全 → 验证器应用」自行启用。首次设置需要当前密码、验证器 App 扫码和一次 6 位动态码确认；确认成功之前，账号仍按原方式登录。

## 用户操作

1. 登录 Web，打开「设置 → 安全」，在「验证器应用」输入当前密码，点击「设置验证器」。
2. 使用支持 TOTP 的验证器应用扫描页面上的二维码；无法扫码时可手动输入页面显示的密钥。二维码完全在浏览器本地生成，不会送往第三方二维码服务。
3. 输入验证器当前的 6 位动态码，点击「验证并启用」。动态码通常每 30 秒更新；手机时间应设置为自动同步。
4. 页面会展示一次恢复码。每个恢复码只能用一次，请离线妥善保存。关闭提示后不会再次展示原码；如需新码，可在安全设置中用当前密码和 TOTP 动态码完成安全验证后重新生成，旧码立即失效。
5. 下次输入邮箱和密码后，登录页会要求动态码；也可以选择「使用恢复码」。如需关闭两步验证，请在「设置 → 安全」完成当前密码与 TOTP 动态码的安全验证；`enforce` 模式下，管理员和主管须先移除特权角色，才能停用 TOTP。

如果设备遗失且没有恢复码，不能仅凭“忘记密码”邮件跳过第二因子。请联系管理员走线下身份核验和有审计记录的人工恢复流程；本版本没有提供管理员一键跳过第二因子的界面。恢复码可完成登录挑战，但不能代替下述敏感操作所需的 6 位 TOTP 动态码。

## 敏感操作安全验证（Phase 2）

以下操作会弹出安全验证：输入当前密码；账号已启用 TOTP 时，还须输入验证器当前的 6 位动态码。**启用 TOTP 后，仅有密码不足以执行这些操作**，即使 `PRIVILEGED_MFA_MODE=optional` 也是如此。

| 用途 `purpose` | 需要安全验证的操作 |
| --- | --- |
| `roles` | 创建、删除用户；修改用户角色或启用/停用用户；管理员重置用户密码 |
| `api-tokens` | 创建、轮换个人 API Token |
| `two-factor` | 停用已启用的 TOTP、重新生成恢复码；直接调用 Better Auth 的已绑定密钥重新获取或替换接口也受保护 |
| `account` | 当前用户删除自己的账号（`/api/auth/delete-user`） |

已有权限校验仍然生效。查看用户或 Token 列表、仅修改用户资料（不提交 `roleNames` 或 `status`）、吊销自己的 API Token，不属于上表的安全验证操作。自助删号仍须满足原有业务限制：有工单或回复记录的账号不能删除；最后一位在职管理员也不能删除。首次绑定尚未启用的 TOTP 仍可用当前密码开始，完成动态码确认后才算启用。

对接 API 时，使用网页登录会话调用 `GET /api/me/security`，读取 `privilegedMfaMode`、`privileged`、`enrolled`、`enrollmentRequired`、`stepUpTtlSeconds` 和 `purposes`。执行操作前调用 `POST /api/me/security/step-up`，请求体包含 `purpose`（`roles`、`api-tokens`、`two-factor` 或 `account`）、`password` 和已启用 TOTP 时必填的 `code`（六位动态码）。响应提供 `stepUpToken` 和 `expiresInSeconds`（300）。把票据放在紧随其后的对应请求的 `X-Step-Up-Token` 请求头中；不要保存在持久存储、日志或工单中。票据绑定用户、当前会话与用途，Redis 原子消费后不能重复使用；过期、用途不符或请求失败后需重新验证。相同 TOTP 码在短时间内不能重复用于申请安全验证；连续尝试过多会触发限流。

上述安全验证只支持网页登录会话，个人 API Token 不能申请或使用票据。已签发的 API Token 不会因启用 TOTP 自动失效；按需审查并吊销旧 Token。直接请求 `/api/auth/two-factor/disable`、`/enable`、`/generate-backup-codes`、`/get-totp-uri` 时，已绑定账号仍须提供 `two-factor` 用途的票据；`/api/auth/delete-user` 则须提供独立的 `account` 用途票据，不能复用其他用途。未配置的删除回调路由 `/api/auth/delete-user/callback` 被拒绝。这些 Better Auth 路由不经过 Nest 的普通接口守卫，不能把其他 `/api/auth/*` 路由一概视为受该票据保护。首次绑定时，未启用、未验证的账号调用 `enable` 或 `get-totp-uri` 不要求票据。

## 安全边界

- TOTP 秘钥和恢复码由 Better Auth 插件加密保存。服务端使用 `AUTH_SECRET` 进行加密；必须长期保管并在多实例间保持一致。丢失或变更密钥可能使既有验证器配置无法使用。
- 邮箱验证完成后不自动登录，防止邮件验证链接绕过已启用的第二因子。
- 密码登录完成第一步时，服务端撤销临时创建的会话；验证第二因子后才签发有效会话。挑战 Cookie 有效期约 10 分钟。动态码和恢复码验证均有尝试次数与账号临时锁定机制。
- 两步验证保护的是**新的交互式密码登录**。启用后不会自动撤销当前/其他设备的会话，也不会撤销已经签发的个人 API Token；如有泄露风险，用户应在「设置 → API Token」手动吊销令牌并更改密码。
- 邮件自助重置密码、管理员重置密码及改密码后，数据库凭据触发器在同一事务中递增用户会话版本；停用账号也递增版本，删除账号后用户记录不存在。每次网页登录会话校验均比对数据库版本，因此即使 Better Auth 的 Redis 会话索引因并发登录漏掉某个令牌，该旧令牌也不能继续认证。密码重置失败且凭据未写入时，版本不会提前增加。密码登录与 TOTP 待验证挑战均绑定发起时的版本，不能跨重置完成登录。此机制不自动吊销个人 API Token；需要时另行审查并吊销。
- Redis 或数据库不可用时不能把无法校验版本的会话当作有效会话；认证请求会失败。恢复到空 Redis 后，会话和未完成的验证流程丢失，用户需重新登录。部署前已有的 Redis 会话按版本 0 处理；首次凭据变更或停用后，即使没有新标记也会失效。
- 恢复码只在创建/轮换时出现在响应与浏览器内存中；不要将二维码、密钥、恢复码、完整请求/响应体写入日志、工单或截图。

## 特权账号部署与恢复

`PRIVILEGED_MFA_MODE` 默认是 `optional`。先以此模式部署，不会因尚未绑定 TOTP 而立即阻断现有管理员/主管的业务接口；逐一让所有 `admin`、`supervisor` 完成绑定、实际验证登录，并确认恢复码已离线妥善保存。之后再把环境变量设为 `enforce` 并重建 API 容器。启用前保留至少一位能正常登录、能获取动态码且有恢复码的管理员；用测试账号先走完操作。`enforce` 下未绑定的管理员/主管访问普通受保护业务接口会被拒绝，只能访问少数账号/安全状态接口并通过 Better Auth 的首次绑定流程完成 TOTP；未绑定的目标用户不能获得特权角色，新建用户也不能直接设为管理员或主管。已有特权账号在该模式下不能停用 TOTP，必须先移除特权角色。

若最后一位管理员丢失验证器但仍有恢复码，可先用恢复码登录；敏感操作仍需 TOTP。若已无可用管理员与动态码，`optional` 回退也**不能**让已绑定账号只凭密码通过登录或敏感操作验证。由获授权的运维人员先核实身份、保全备份并记录审批与审计信息，在维护窗口通过受控数据库恢复流程清除该账号的 `twoFactor` 绑定记录并将 `users.twoFactorEnabled` 恢复为 `false`，保持两处状态一致；同时检查并撤销有风险的会话和 API Token。恢复访问后立即重新绑定、验证 TOTP，离线保存新恢复码，再确认所有特权账号满足条件后使用 `enforce`。此流程属于人工应急恢复；应用当前没有自助或管理员一键跳过 TOTP 的功能。不要把 `AUTH_SECRET` 轮换或重置密码当成第二因子恢复办法。

## 开发与部署

随版本部署 `apps/api/prisma/migrations/20260928090000_two_factor`、`20260928120000_last_active_admin` 和 `20260928130000_session_epoch`；生产 API 启动时执行 `prisma migrate deploy`。依次安装 TOTP 表与字段、最后在职管理员保护触发器，以及 `users.session_epoch`（存量用户默认 0）和凭据变更触发器。**会话撤销保证依赖第三个迁移中的触发器**；仅运行 `prisma db push` 会创建列但不会安装触发器，不能视为完成安全部署。生产 API 启动时核查五个安全触发器，缺失则拒绝启动。`NODE_ENV=development` 的开发 API 在 `db push` 后核对列类型、非空及默认值，并在事务锁下从迁移 SQL 幂等安装缺失的安全触发器；不会修改 `_prisma_migrations`，且不会在生产模式自动补装。开发库若已通过 `db push` 建出 TOTP 结构但迁移历史仍待应用，先在隔离副本核对实际结构和迁移记录，再由运维人员有依据地协调迁移；不要直接重跑会冲突的迁移、盲目 `migrate resolve` 或重置共享库。不会强制存量用户立即启用 TOTP。API 与 Web 的 `better-auth` 必须保持相同版本（当前 1.6.23），不要仅升级单侧。

部署前请检查数据库备份及 `AUTH_SECRET`，部署后用测试账号验证以下路径：未启用时可登录；扫码后错误动态码不启用；正确动态码启用；密码验证后 `/api/me` 仍不能访问；正确动态码完成登录；单个恢复码首次可用、重复使用无效；已启用时仅密码不能申请敏感操作票据；正确密码和 TOTP 可以完成一次指定用途操作，重复使用票据失败；用户状态变更和自助删号分别需要 `roles`、`account` 用途；管理员重置密码后目标用户旧会话失效；关闭后密码登录恢复正常。不要用唯一的生产管理员账号做首次试验。

如系统采用邮件发送，邮箱验证流程现在验证后返回登录页，不再自动建立会话。个人 API Token 认证方式不变。
