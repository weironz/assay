# 两步验证（验证器应用）

本系统使用 Better Auth 1.6.23 的 two-factor 插件实现 TOTP。**登录验证与操作授权是两件事**：启用验证器后登录仍需第二因子；登录后的用户在自己权限内执行操作，不再弹出额外密码/TOTP 验证窗口。

## 用户操作

1. 登录 Web，打开「设置 → 安全 → 验证器应用」，填写当前密码，点击设置验证器。
2. 使用 TOTP 应用扫描二维码，或手动输入密钥。二维码在浏览器本地生成，不发往第三方服务。
3. 输入当前六位动态码并确认；确认成功前不算启用。请将手机时间设为自动同步。
4. 页面仅展示一次恢复码，每个码只能用一次，请离线妥善保存。重新生成时填写该设置的内联密码表单，旧恢复码立即失效。
5. 下次密码登录后仍须输入动态码或恢复码。停用验证器使用安全设置中的内联密码表单；`enforce` 模式下特权账号须先移除特权角色才能停用。

当前密码是 Better Auth 对停用验证器、轮换恢复码、注销账号等设置本身的必需输入，**不是额外二次验证弹窗**；不再叠加一次操作 TOTP。首次绑定验证器的动态码用于验证新密钥，登录第二因子也继续保留。

## 操作授权策略（2026-10-20 更新）

- 管理员修改用户角色、受委派岗位执行 AD/共享管理、普通用户创建/轮换自己的 Token 等，直接使用当前 Web 会话，不重复索取密码或动态码。
- 后端仍检查当前权限、有效且未撤销的会话、账号状态及受信 Origin；这不是关闭 RBAC，也不会赋予普通用户管理能力。
- API Token 不能代替 Web 会话修改账号或管理设置；其原有 scopes 和数据可见范围不变。
- 变更审计、请求幂等、密码修改限流、最后一位有效管理员保护及“有工单/回复记录不能自助删号”继续生效。
- 原有业务删除确认和操作表单仍可保留；本次移除的是操作前额外的密码/TOTP 安全挑战弹窗。

`GET /api/me/security` 保留响应契约。正常会话的 `stepUpExemptPurposes` 包含 `roles`、`api-tokens`、`samba`、`account`、`two-factor`。会话写入带 Cookie 和受信 Origin 即可，无须先调用 `POST /api/me/security/step-up`。

旧 step-up 接口和 `X-Step-Up-Token` 为兼容旧客户端保留。显式提交票据时，仍要求票据有效、用途匹配、与当前用户/会话绑定且未被消费；无效票据不能降级成会话放行。票据有效期 300 秒，不可持久化或写入日志。

直接调用 Better Auth 的 `/api/auth/two-factor/disable`、`/enable`、`/generate-backup-codes`、`/get-totp-uri`、`/delete-user` 等账号接口，仍有独立的会话、账号状态及来源保护，并保留 Better Auth 本身的密码要求；不能假设这些路由经过 Nest 普通守卫。未配置的 `/api/auth/delete-user/callback` 继续拒绝。

## 安全边界

- TOTP 密钥和恢复码加密存储，依赖原 `AUTH_SECRET`。密钥须长期保管，多实例一致；丢失或变更可能使原验证器不可用。
- 邮箱验证后返回登录页，不自动登录，避免绕过第二因子。
- 密码登录完成第一步时撤销临时会话；第二因子通过后才签发有效会话。挑战 Cookie 约十分钟有效，动态码和恢复码均有尝试次数及账号锁定限制。
- 两步验证保护新的交互式密码登录；启用后不自动撤销其他设备会话或已有 API Token。有泄露风险时应改密码并审查/吊销 Token。
- 密码变更、重置、账号停用通过数据库触发器递增会话版本；每次认证比对该版本，旧会话及重置前发起的密码/TOTP 挑战不能跨重置继续认证。此机制不自动吊销 API Token。
- Redis 或数据库不可用时认证失败，不信任无法核验的 Cookie。恢复到空 Redis 后需重新登录，未完成验证流程也会丢失。
- 不要把二维码、密钥、恢复码或完整认证请求/响应写入日志、工单和截图。恢复码只在生成时存在于响应与浏览器内存。

## 特权账号部署与恢复

`PRIVILEGED_MFA_MODE` 默认 `optional`。逐一确认所有特权账号已实际完成 TOTP 登录、恢复码已离线保管后，才设为 `enforce` 并重建 API。启用前保留至少一位可正常登录的管理员。`enforce` 下未绑定的特权账号只能访问少数账号/安全接口及首次绑定流程；目标账号未完成绑定不能获得特权角色，已绑定特权账号不能停用验证器。这一登录/准入策略不因移除操作弹窗而取消。

设备遗失但有恢复码时，可用恢复码登录后按当前权限操作；没有恢复码时，忘记密码邮件或切换 `optional` 均不能跳过已绑定的登录第二因子。经授权的运维人员应先线下核验身份、保全备份、记录审批审计，在维护窗口受控清除该账号 `twoFactor` 记录并把 `users.twoFactorEnabled` 设为 `false`，保持两处一致，并撤销有风险的会话/Token。恢复后立即重新绑定、验证、保管恢复码。应用没有管理员一键跳过 MFA 功能，不要将轮换 `AUTH_SECRET` 或重置密码当作第二因子恢复办法。

## 开发与部署验证

生产使用 `prisma migrate deploy`，必须包含 `20260928090000_two_factor`、`20260928120000_last_active_admin`、`20260928130000_session_epoch` 等安全迁移。`db push` 只创建结构，不安装这些触发器；不能替代生产迁移。生产启动检查五个安全触发器，缺失则拒绝启动。

开发模式可在 `db push` 后核验列约束，并从迁移 SQL 幂等补装安全触发器；不修改 `_prisma_migrations`。若开发库实际结构已建立而迁移记录待应用，先在隔离副本核对，不要盲目 migrate resolve、重跑冲突迁移或重置共享库。

API/Web 的 better-auth 版本必须一致（1.6.23）。部署前备份数据库和 `AUTH_SECRET`；用非唯一生产管理员的测试账号验证：

- 未启用可登录；错误绑定码不启用，正确码启用。
- 密码第一步后受保护接口仍拒绝；正确 TOTP 或一次性恢复码才完成登录，恢复码不能复用。
- 登录后权限内的角色修改、Token、AD 管理不弹出二次验证；越权、过期会话、不受信来源仍拒绝。
- 修改密码/管理员重置密码后旧会话失效；最后有效管理员不能被删除或停用。
- 停用验证器、恢复码轮换在内联表单完成；`enforce` 禁止特权账号停用；旧显式票据仍不能复用。
