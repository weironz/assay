# GreenStor COP 第一阶段改造方案与实施计划

版本：2026-10-12。目标：在现有 Assay 开发环境增量建设 GreenStor Company Operations Platform（公司运营服务平台），交付资产管理与备品备件管理。现有工单、认证、MFA、CLI/MCP、分享和数据保持兼容。

## 1. 范围与默认业务规则

- 模块化单体：NestJS、React、PostgreSQL/Prisma、Redis/BullMQ、现有存储与 Docker 保留。不开设微服务，也不引入低代码/BPMN 引擎。
- 资产：唯一资产编号、可选序列号、名称/分类/型号/厂家、部门/责任人/位置、机房/集群、采购与保修信息；待核对登记、在库、在用、维修、退役；检索、分页、编辑、履历、附件、工单关联和 CSV 导出。
- 备件：唯一 SKU、名称/分类/型号/厂家、单位、最低库存、启用状态；仓库；按备件/仓库查询余额；入库、领用、退回、调拨、盘点调整及冲销；可关联工单/资产；低库存提示、不可变库存流水、CSV 导出。
- 初期数量为整数（件/套/个等），单次库存业务处理一种备件；批次、序列化备件、采购订单、成本核算、折旧及 ERP/财务对接不在本期。金额用 Decimal，不用浮点运算。
- 仅管理员、资产管理员、仓库管理员和平台观察员有相应模块权限。初期业务管理员的范围为公司；普通工单角色不会自动获得资产或库存权限。组织、模块动作权限与业务访问规则分别实现，后续部门/仓库范围可在模块访问策略扩展。
- 新增部门层级及员工部门归属。固定业务角色继续随代码发布，保持现有安全策略；不开放任意权限编排。

## 2. 领域模型与一致性

新增 Department、Asset、TicketAsset、SparePart、Warehouse、StockBalance、InventoryOperation、StockMovement、BusinessActivity、BusinessAttachment、AssetImportBatch。User 新增可空 departmentId；历史工单定位字段保留。

StockBalance 是可重建余额，StockMovement 是不可变事实。业务操作、全部余额变更、对应流水与审计在同一数据库事务内提交。调拨同时提交源扣减和目标增加。盘点记录差额及原因。冲销生成反向操作且原单最多冲销一次；库存不足时拒绝冲销。无余额直接修改 API。

使用 Serializable 事务、条件扣减和有限并发重试，禁止负库存；PostgreSQL CHECK 约束提供兜底。客户端每次操作生成幂等键，重复相同请求返回原结果，复用键但更改请求返回 409。库内保存请求摘要，操作人参与摘要。退役/停用替代删除，保持履历与引用。

资产与工单通过有外键的关联表连接，可关联多台资产；关联工单仍校验当前用户的工单可见性。资产履历展示可见工单，不通过资产 API 暴露本来无权读取的工单。

## 3. 平台能力与未来适配

- 增加模块权限码及专用角色；既有工单权限不改变。
- 公共 BusinessRef 使用受控 kind + id，模块适配器负责存在性与读写权限。业务审计、附件和通知通过适配器复用，不将所有业务塞进 Ticket.extra。
- BusinessActivity 在业务事务内写入，包含操作者、动作、业务引用与变更快照；库存流水不可改写。
- BusinessAttachment 复用原 StorageDriver、上传限制与流式下载，但按业务引用检查权限。原 TicketAttachment 保留兼容。
- 通知支持受控业务链接，同时保留 ticketId 与工单通知行为。
- 请假/报销未来建立独立业务表，复用组织/权限/文件/审计/通知；审批适配协议为 submit、approve、reject、withdraw，与业务状态分开。未来流程定义须版本化，运行实例绑定版本；通过事务中的业务事件衔接。初期只记录协议与扩展点，不提供虚假的审批功能或占位页面。

## 4. 增量迁移与部署

1. 先提交方案与计划，再实施代码。使用现有 checkout，不创建 worktree。
2. 新增迁移只增加表、索引和可空字段，禁止重置数据库或删除历史工单/附件。
3. 迁移前在 dev 保存数据库备份，记录工单数量。运行 Prisma migration deploy，生成 Client 和幂等 seed，重启 api/web 的必要进程。
4. 开发源代码卷保持热更新；更新 Compose 生成文件时保留平台代理、CA、同源 API、NetBird/SSH 和现有卷。
5. 生产发布/外部服务器部署不在本次授权范围。

## 7. 实际数据及资产身份设计

2026-10-12 收到两份用户上传的原始工作簿。ReadyIDC 角色对齐版有 74 台设备，已带 GS-000059～GS-000132；Datazone 表有 58 台设备，没有 GS 号。用户明确授权按 Datazone 设备清单原有行序分配 1～58，最终在 COP 保留/分配 GS-000001～GS-000132。不是按机柜、角色或后续排序重新编号。实物与标签核验保持待确认；后续新设备下一号为 GS-000133，退役不复用编号。

复核用户提供的背景记录后，以提供的凭据对 https://netbox.cloudcele.com 做一次受控 HTTPS 登录和只读设备查询，共 132 台，全部与 Excel 设备协调匹配；NetBox 资产标签当时均为空。只读取设备元数据，不创建 PAT、不回写。`dz-chonburi` 与 Datazone 是同一站点的明确别名；旧 `b300` 角色归为 gpu-server。NetBox 负责技术对象关联，COP 管理编号、归属、责任人、采购、核验与业务履历。源对象 ID 不作为公司资产编号，源技术状态不等于 COP 登记确认。

缺少 SN 的两台设备保留原状并提示核对，不补造 SN。所有权、责任人和采购没有可靠数据，因此导入为待核对/所有权未确认，而非自动推定自有或已验收。在 COP 分配 GS 不修改原工作簿、不代表 NetBox 已写入、不代表实物贴标完成。原工作簿、访问凭据和逐台映射保存在仓库外的受限文件中，不提交代码仓库。

本期实现 XLSX/CSV 设备表白名单解析、导入预览/冲突检查、原子提交/幂等与可选只读 NetBox API 连接。已有 132 台实机导入开发库，账号密码表不入库；GPU/磁盘/光模块硬件清单代表设备内已安装组件，不能推算成可用备件库存。备件目录、仓库和真实期初数量待盘点后通过入库登记。
